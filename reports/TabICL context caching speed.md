# TabICL's KV cache speeds reuse, not fitting

Yes, TabICLv2 can be stopped from re-reading its training context on every prediction call. Since tabicl v2.0.0 the switch is `TabICLClassifier(kv_cache=True)` (or `"kv"`). It runs the training rows through the network once, during `fit()`, stores each layer's key/value projections, and then sends only the test rows through at predict time. Because test rows only ever attend to training rows, the cache is exact. On this project's own folds the AUC matched to five decimals. Caching makes **repeat** predictions much faster: on the paper's data, on a 4-core CPU, a second 300-cell prediction against the same fitted context dropped from about 105 s to 2.8 s for loggerhead (38x) and from 758 s to 22 s for blue whale (35x; the 758 s is a `repr`-mode repeat, used as the no-cache stand-in). It does **not** make a single fit-then-predict faster. It makes it slower (1.16x for loggerhead, 1.55x for blue whale), because the whole train-side forward pass moves into `fit()`, which grows from about 2 s to 110–1,140 s. Peak memory also rose to 5.0 GB on a 5.9 GB machine. TabPFN's `fit_mode="fit_with_cache"` makes the same trade, with the same "only pays off on repeated predicts" caveat. For the paper, caching cannot rescue any claim that TabICLv2 is faster than a Random Forest. Even fully cached, one TabICLv2 re-prediction of 300 cells (2.6–22 s) takes longer than fitting **and** predicting a fixed RF from scratch (about 2 s). The defensible claim is narrower. TabICLv2 avoids per-species gradient training and hyperparameter search, and once a species' context is cached, each extra scenario costs seconds instead of minutes compared with uncached TabICLv2.

## kv_cache stores the training context once, and the shortcut is exact

The feature shipped with the TabICLv2 code release, **v2.0.0 (12 February 2026)**. In v2.0.3 it moved from a `fit()` argument to a constructor argument "following scikit-learn convention", so on the locally installed v2.1.1 it must be passed as `TabICLClassifier(kv_cache=...)` ([GitHub releases](https://github.com/soda-inria/tabicl/releases)). The README pitches it for exactly this problem: "To speed up repeated inference on the same training data, enable KV caching. The cache is built during `fit` and reused across `predict` calls" ([README](https://github.com/soda-inria/tabicl)). Before v2, `fit()` fit only the preprocessors, and "`predict()` performs a forward pass of the Transformer with the entire training+test data". That is the re-reading behaviour the question describes, and it is still the default (`kv_cache=False`) ([Issue #6](https://github.com/soda-inria/tabicl/issues/6)).

There are two cache modes. **`"kv"`** stores the key/value projections of the column-embedding ISAB blocks plus the train-row K/V at **every one of the 12 ICL transformer layers**. At predict time, only the test rows pass through the network, and they attend to the cached train K/V. **`"repr"`** stores the column-embedding K/V and the 512-d row representations (with labels "baked in"). It uses "~24x less memory than 'kv' for the ICL part, at the cost of re-running the ICL transformer at predict time" ([API docs](https://tabicl.readthedocs.io/en/latest/api.html); [kv_cache.py](https://github.com/soda-inria/tabicl/blob/v2.2.0/src/tabicl/_model/kv_cache.py)). The 24x matches 12 layers × (K + V) versus one vector per row.

Caching is lossless because of the architecture, not by approximation. In the column stage, "only train samples serve as keys and values" for the inducing points, and in the ICL stage "the embeddings in H_train can attend to one another while those in H_test can only attend to H_train" ([TabICL paper](https://arxiv.org/html/2502.05564)). TabICLv2 keeps that rule: "test samples attend to training samples for prediction" ([TabICLv2 paper](https://arxiv.org/html/2602.11139)). No test row ever changes a training row's representation, so the train-side states can be computed once and reused. The local benchmark confirmed this: AUC was **identical to five decimals on every fold**, and a synthetic smoke test gave a maximum probability difference of 1.3e-4, which is float noise ([local benchmark](<../research_notes/TabICL context caching speed/local_kv_cache_measurement.md>)).

The cache can also outlive the Python session. `est.save(path, save_kv_cache=True)` pickles the fitted estimator with its cache moved to CPU. You can even drop the raw training data, since "the KV cache encodes the training context and enables prediction without raw data" ([base.py @ v2.2.0](https://github.com/soda-inria/tabicl/blob/v2.2.0/src/tabicl/_sklearn/base.py)). One caveat matters here. A get/set-state bug that dropped `model_kv_cache_` during pickling was fixed only in **v2.2.0**, so the local v2.1.1 install should be upgraded, or round-trips checked, before relying on persisted caches ([PR #124](https://github.com/soda-inria/tabicl/pull/124)).

## On this project's CPU, caching shifts 110–1,140 s into fit

The local benchmark replayed the paper's spatial leave-one-region-out folds: 6 features, 300-cell class-balanced test sets, `n_estimators=2`, CPU-only torch on a 4-core WSL2 machine with 5.9 GB RAM. "predict2" is a second, independently drawn 300-cell test set from the same held-out region, scored against the same fitted context. It stands in for a new scenario or time slice. In the table below, loggerhead values are means over folds 1, 3 and 4. Fold 0 was slow in every mode, which looks like a first-fold warm-up effect. Blue whale is fold 2 only ([local benchmark](<../research_notes/TabICL context caching speed/local_kv_cache_measurement.md>)).

| Species (context rows) | Mode | fit (s) | first predict (s) | fit + first predict (s) | repeat predict (s) | peak RSS (GB) |
|---|---|---|---|---|---|---|
| Loggerhead (10.3k–11.2k) | none | 2.3 | 106.5 | 108.8 | 105.2 | 2.29 |
| Loggerhead | repr | 19.4 | 108.7 | 128.2 | 85.4 | 1.87 |
| Loggerhead | kv | 122.6 | 3.3 | 125.9 | 2.8 | 3.08 |
| Blue whale (33.9k) | none | 1.8 | 794.2 | 796.0 | ≈ first predict | n/a |
| Blue whale | repr | 60.3 | 797.9 | 858.2 | 758.5 | 3.23 |
| Blue whale | kv | 1142.4 | 89.1 | 1231.4 | 21.8 | 5.01 |

Peak RSS for loggerhead is the four-fold process peak. Fixed and tuned RF on the same folds are in the [earlier benchmark](<../time.csv>).

The pattern is clear. With `kv`, **the first predict is not where the cost disappears. It moves into `fit()`**, which grows about 50x for loggerhead and about 600x for blue whale. Fit plus one predict ends up **1.16x slower** for loggerhead (109 s → 126 s) and **1.55x slower** for blue whale (796 s → 1,231 s). The real payoff comes from every later call on the same context: **38x faster** for loggerhead (105 s → 2.8 s) and **35x** for blue whale (758 s → 22 s, where 758 s is the `repr` repeat predict, which re-runs the full ICL transformer and so stands in for no cache). Cumulative wall-clock breaks even at the **second predict call** for both species. Over ten calls the totals are 1,056 s vs 151 s (loggerhead) and 7,622 s vs 1,427 s (blue whale). Scoring the whole basin (13,683 cells, fold 0) took 514.6 s without a cache and 131.6 s with one, about 10 ms per cell cached. Counting the fit, the cached run won even on that single large call (400.8 s vs 516.6 s). That rests on one warm-up-affected fold, so treat it as indicative ([local benchmark](<../research_notes/TabICL context caching speed/local_kv_cache_measurement.md>)).

**`repr` buys almost no time on this data.** Its first predict (108.7 s) is no faster than no cache (106.5 s). It skips only the column and row stages for training rows, and with six features those stages are cheap. The 12-layer ICL transformer over train plus test, which dominates the cost, still runs on every call. Its value is memory, not speed: it had the lowest peak RSS of the three modes for loggerhead.

On CPU, the cache build also costs more than the forward pass it replaces. In principle, cache build plus cached predict should equal one uncached forward pass. Locally there was 16% overhead for loggerhead and 55% for blue whale. Neither the docs nor the cache-building code explain this ([classifier.py @ v2.2.0](https://github.com/soda-inria/tabicl/blob/v2.2.0/src/tabicl/_sklearn/classifier.py)). One plausible reason is that the per-layer K/V tensors are materialised and concatenated. For blue whale, memory pressure close to the machine's 5.9 GB ceiling (with swap available) is a likely amplifier. That is an inference, not a measurement. Published GPU figures look better. PriorLabs' TabPFN-3 report finds that building the cache "costs essentially the same as the cold fit+predict at every measured shape" on an H100 ([arXiv 2605.13986](https://arxiv.org/abs/2605.13986)). The local CPU result is therefore somewhat worse than the GPU literature implies, but it agrees on the main point: caching does not shorten the first call.

## Memory, not speed, sets the ceiling on a 6 GB laptop

The `kv` cache grows linearly with training rows × ensemble members. A rough estimate from the architecture (12 layers × K and V × 512 dims × 4 bytes) gives **about 48 KB per training row per ensemble member in fp32**, against about 2 KB for `repr`. The authors publish no formula, so this is derived, not documented ([API docs](https://tabicl.readthedocs.io/en/latest/api.html)). For the blue whale context of 33.9k rows with two members, that comes to roughly 3.3 GB. That fits the measured **5.0 GB peak RSS** once the model weights and data are added. One user reported about 5 GB of cache at 40k rows × 250 features, and the maintainer answered that "setting `kv_cache="repr"` can largely reduce memory consumption at the cost of more computations" ([Issue #92](https://github.com/soda-inria/tabicl/issues/92)). At the library default of `n_estimators=8`, the same whale context would need around 13 GB of cache. **The machine used for the paper could not run default-ensemble `kv` caching on its larger species contexts**, and the 29–30k-row basking-shark folds sit in the same range ([earlier benchmark](<../time.csv>)). This is the practical trade-off. `kv` is fast but memory-bound. `repr` is lean but, with few features, no faster than no cache. With no cache, every call pays the full quadratic train-side attention again.

## TabPFN's fit_with_cache makes the same bargain, documented more loudly

PriorLabs' `tabpfn` has four fit modes. The default, `"fit_preprocessors"`, caches only the preprocessed training data, so every `.predict()` still reruns the full transformer over train plus test. In that respect it matches TabICL's `kv_cache=False`. `"fit_with_cache"` also initialises "the transformer key-value cache ... allowing for much faster inference on the same data at a large cost of memory. Ideal with very high GPU memory and multiple calls to .predict() with the same training data" ([tabpfn classifier.py](https://github.com/PriorLabs/TabPFN/blob/main/src/tabpfn/classifier.py)). PriorLabs' own guidance says the cache suits "repeated predictions against the same fit, including repeated calls from explainability tools", that memory "scales with training-set size and number of estimators", and that a cache "is valid only for the training data and model configuration used to create it" ([PriorLabs KV cache docs](https://docs.priorlabs.ai/capabilities/kv-cache)).

| | TabICLv2 `kv_cache` | TabPFN `fit_mode="fit_with_cache"` |
|---|---|---|
| Default | `False` (re-reads context each predict) | `"fit_preprocessors"` (re-reads context each predict) |
| What is cached | Column-ISAB K/V + all 12 ICL layers' train K/V (`"kv"`), or train representations (`"repr"`) | Per-estimator transformer KV state for training rows |
| Memory lever | `"repr"` mode (~24x smaller ICL part) | `kv_cache_precision` int8/fp8 (TabPFN-3), `keep_cache_on_device=False` |
| Cache scales with | Rows × estimators (features compressed away) | Cells (rows × features) × estimators |
| Published memory | None official; user reports ~5 GB at 40k × 250 | TabPFN-2.5: 6.1 KB GPU + 48.8 KB CPU per training cell |
| CPU size limits | None enforced | Refuses >1,000 rows (v2/2.5) or >5,000 rows (v3/3.5) on CPU unless overridden |
| Persistence | `save(save_kv_cache=True)` | `save_fitted_tabpfn_model` |

Sources for the table: [tabicl API docs](https://tabicl.readthedocs.io/en/latest/api.html), [Issue #92](https://github.com/soda-inria/tabicl/issues/92), [tabpfn source and README](https://github.com/PriorLabs/TabPFN), [TabPFN-2.5 report](https://arxiv.org/html/2511.08667), [TabICL paper](https://arxiv.org/html/2502.05564).

The published speedups mostly come from different settings than this project's measurements. The TabPFN v2 Nature paper reports caching speedups of "around 300× on CPU (from 32 s to 0.1 s) and 6× on GPU" at 10,000 training rows × 10 features, and 800× on CPU at 100 features ([Hollmann et al., Nature 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC11711098/)). These are **predict-only** numbers, measured after the train state was built. The TabPFN-3 report gets 342 ms cold vs 22 ms cached on an H100, while the cache build costs as much as the cold run ([arXiv 2605.13986](https://arxiv.org/abs/2605.13986)). PriorLabs' cookbook shows about 5.5x on one predict at 5,000 rows on unstated hardware ([PriorLabs cookbook](https://docs.priorlabs.ai/cookbook/faster_performance_with_cache)). Molnar measured TabICL itself on a GPU going from 0.5 s to 0.09 s with the cache ([Mindful Modeler](https://mindfulmodeler.substack.com/p/making-tabular-foundation-models)). The local **35–38x** for TabICLv2 is also predict-only, on CPU. It lands between the GPU figures (5–30x) and TabPFN's CPU figures (300–800x). Those headline multipliers do not carry over to fit plus predict, where the local result is a slowdown. One practical difference counts against TabPFN here: its package refuses CPU training sets above 1,000 rows for v2/2.5 by default ([TabPFN README](https://github.com/PriorLabs/TabPFN)). This project's 10k–35k-row contexts would need an override even to try it on the same machine.

## Fewer estimators, smaller contexts and distillation cut cost in single runs

Caching helps only with reuse, so the levers for a single fit-then-predict per spatial fold are different. **Ensemble size** is linear and independent of context. On a small dataset, Molnar measured TabICL at 0.42, 0.22, 0.11 and 0.06 s for 8, 4, 2 and 1 estimators, with log-loss moving only from 0.0671 to 0.0717 between 8 and 4 ([Mindful Modeler](https://mindfulmodeler.substack.com/p/making-tabular-foundation-models)). The paper already runs `n_estimators=2`, so little is left to gain here. **Hardware** is the largest lever. The same blog found CPU at about 15 s vs GPU at about 0.5 s (~30x) for TabICL. TabICLv2's authors benchmark on an H100, where they "fit and predict a dataset with 50,000 samples and 100 features in under 10 seconds" ([README](https://github.com/soda-inria/tabicl)). The CPU-specific knobs are weak. `use_amp` does nothing on CPU, and the v2.2.0 docstring says forcing bf16 "was much slower than fp32" ([classifier.py @ v2.2.0](https://github.com/soda-inria/tabicl/blob/v2.2.0/src/tabicl/_sklearn/classifier.py)). Since v2.2.0 the thread count is the maximum of logical cores and `n_jobs`, so a positive `n_jobs` cannot cap threads below the logical-core count. Nested inside a parallel CV loop, that can oversubscribe the CPU ([GitHub releases](https://github.com/soda-inria/tabicl/releases)).

**Shrinking the context** attacks the quadratic term directly. Going from 30k to 5k rows cuts train-to-train ICL work about 36x. The literature warns about accuracy, though: with random subsampling, TabPFN "plateaus and declines as dataset size increases", while kNN-local contexts keep improving ([LoCalPFN, arXiv 2406.05207](https://arxiv.org/html/2406.05207)). TabDPT reports "a consistent drop" in accuracy when retrieval is removed ([TabDPT, arXiv 2410.18164](https://arxiv.org/html/2410.18164)). Per-query retrieval also defeats caching, since each query gets its own context. **Linear attention** (TabFlex) and **distillation** go further. TabPFN-2.5-as-MLP/TreeEns claims "much faster inference speed than TabPFN" ([TabPFN-2.5, arXiv 2511.08667](https://arxiv.org/html/2511.08667)), while MotherNet's independent test of MLP distillation cost about 0.05 normalised AUC (0.850 → 0.802) ([MotherNet, arXiv 2312.08598](https://arxiv.org/html/2312.08598)). PriorLabs itself sells distillation, not caching, as the route to "sub-millisecond latency" on CPU ([arXiv 2605.13986](https://arxiv.org/abs/2605.13986)). That tells you the vendor does not think caching alone reaches tree-model speed.

## The paper can claim cheap reuse, not speed over Random Forest

The reviewer is right, and caching does not change the verdict. On the paper's own folds and machine, uncached TabICLv2 fit plus predict took **114–804 s**. A fixed 200-tree RF took **1.4–3.5 s**, and an RF with full nested-CV tuning (66–130 fits) took **106–317 s** ([earlier benchmark](<../time.csv>)). With `kv`, a single fit plus predict gets slower (117–1,231 s). In the cross-validation experiments each held-out region has a new context and is predicted once, so **caching yields zero benefit for any number the paper currently reports**. Even the cached marginal cost loses to the trees. A cached 300-cell re-prediction (2.6–22 s) takes longer than a fixed RF's entire fit plus predict (about 2 s), and about 10–240x longer than the RF's own predict step (0.06–0.23 s) ([local benchmark](<../research_notes/TabICL context caching speed/local_kv_cache_measurement.md>); [earlier benchmark](<../time.csv>)). Independent GPU benchmarks agree in direction. TabArena puts default TabICL's predict at 1.48 s per 1K rows on an L40S GPU against default RF's 0.05 s on CPU. TFMs pull ahead only of **tuned-and-ensembled** GBDTs, whose training runs to hundreds or thousands of seconds per 1K rows ([TabArena, arXiv 2506.16791](https://arxiv.org/abs/2506.16791)). Even the famous "2.8 s vs 4-hour-tuned ensemble" TabPFN result compares a GPU forward pass against tuning, not against an untuned RF ([Nature 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC11711098/)).

"Amortized" can survive if it is defined precisely. The amortization lives in **pretraining**: TabICLv2 needs no per-species gradient training and no hyperparameter search, which removes a tuning loop and its researcher degrees of freedom. The KV cache adds a second, measurable sense. Once a species' context is encoded, each extra climate scenario or time slice costs only test-to-train attention. Ten scenarios cost 151 s instead of 1,056 s for loggerhead, and 1,427 s instead of 7,622 s for blue whale. At ten scenarios, cached loggerhead TabICLv2 (151 s) roughly matches a single tuned-RF fold (117–168 s). The tuned RF still predicts those scenarios almost for free after fitting, so this is parity at best, never an advantage. The blue whale cached total stays an order of magnitude above tuned RF (106–117 s). These numbers matter only if the paper actually scores many scenarios against a fixed context. An earlier project decision reframed the work as a transferability audit because the data are too short for true climate projection, so that use is prospective, not demonstrated.

A concrete rebuttal could read:

> We thank the reviewer and agree that our wording implied a speed advantage we do not have. On our CPU (4 cores, `n_estimators=2`), TabICLv2 takes 114–804 s per fold versus about 2 s for a fixed Random Forest and 106–317 s for a nested-CV-tuned Random Forest. We now report these wall-clock times in Table X. By "amortized" we mean that learning is amortized into pretraining: no per-species training or hyperparameter search is performed. We do not claim lower compute than Random Forest. TabICLv2's optional KV cache (exact, AUC unchanged) encodes a species' training context once; afterwards each additional scenario costs 2.6–22 s per 300 cells instead of 105–758 s. That is a 35–38x reduction relative to uncached TabICLv2, though still slower than Random Forest prediction. We have revised the abstract and title accordingly.

The title's "Climate-Scale" should be reconsidered as well. It implies a throughput claim that the CPU numbers do not support, and the cache's 5 GB peak at `n_estimators=2` shows that scaling to the library default ensemble would exceed the machine used.

## Conclusion

The question has a clean answer in two halves. Avoiding the re-read is easy, exact and documented: one constructor flag. But it moves cost into `fit()` rather than removing it. On a CPU the move is not free: building the cache cost 16–55% more than the forward pass it replaced, and peak memory nearly doubled. Caching therefore turns TabICLv2 into a model that is expensive to load and cheap to query again, the same profile TabPFN advertises. It does not make TabICLv2 a cheap model. For this paper, the honest efficiency story is about tuning effort and marginal cost per extra scenario, not wall-clock compute against trees. The one experiment that would make the amortization claim concrete is scoring a real set of scenarios against a cached context, reported next to RF's equivalent cost.

Two things remain unknown and are worth checking before the camera-ready. One is whether a GPU run, which the paper's machine lacks, would put cached TabICLv2 near tuned RF on total cost; Molnar's figure suggests roughly a 30x CPU penalty for TabICL, but nobody has measured it on these data. The other is whether the v2.1.1 pickling path keeps the cache intact. That only matters if the paper wants to claim that the cached context can be saved once and reused across sessions.
